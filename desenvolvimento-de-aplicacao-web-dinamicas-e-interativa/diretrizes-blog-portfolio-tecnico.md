# Diretrizes de Estrutura do Blog e Portfólio Técnico

## Índice de páginas

1. [Página 1 — Home](#página-1--home)  
   Página de entrada do site. Apresenta quem você é, o propósito do blog e direciona o visitante para artigos, trilhas, projetos e canais profissionais.

2. [Página 2 — Artigos](#página-2--artigos)  
   Centraliza todos os conteúdos publicados e permite que o usuário encontre artigos por tema, tecnologia, nível, trilha ou busca.

3. [Página 3 — Página de artigo](#página-3--página-de-artigo)  
   É a principal experiência de leitura do site. Deve demonstrar conhecimento técnico, clareza de comunicação e capacidade de ensinar.

4. [Página 4 — Trilhas de aprendizado](#página-4--trilhas-de-aprendizado)  
   Organiza conteúdos em sequências lógicas de estudo, ajudando o visitante a entender como os assuntos se conectam.

5. [Página 5 — Página de trilha](#página-5--página-de-trilha)  
   Mostra o caminho completo de aprendizado de um tema, com módulos, níveis, pré-requisitos, artigos e projetos relacionados.

6. [Página 6 — Projetos](#página-6--projetos)  
   Reúne os projetos usados como demonstração prática das habilidades técnicas e como base para os artigos do blog.

7. [Página 7 — Estudo de caso do projeto](#página-7--estudo-de-caso-do-projeto)  
   Explica o raciocínio por trás de cada projeto: problema, decisões técnicas, arquitetura, desafios, trade-offs, testes e aprendizados.

8. [Página 8 — Tecnologias](#página-8--tecnologias)  
   Organiza o conhecimento por tecnologia e conecta artigos, trilhas e projetos relacionados a cada stack.

9. [Página 9 — Sobre](#página-9--sobre)  
   Apresenta trajetória, interesses, forma de aprender, áreas de estudo e posicionamento profissional.

10. [Página 10 — Agora](#página-10--agora)  
    Mostra no que você está trabalhando, estudando e explorando atualmente.

11. [Página 11 — Busca](#página-11--busca)  
    Permite pesquisar artigos, trilhas, projetos e tecnologias em um único lugar.

---

# Página 1 — Home

## Para que a página serve

A Home deve apresentar rapidamente quem você é, o que o visitante encontrará no site e quais são os principais caminhos de navegação.

Ela deve funcionar como uma porta de entrada para o blog e para o portfólio, sem tentar mostrar todo o conteúdo existente.

A Home precisa transmitir:

- confiança;
- conhecimento técnico;
- modernidade;
- organização;
- clareza;
- personalidade;
- profissionalismo.

## O que deve ter

### Hero principal

O hero deve conter:

- seu nome;
- uma apresentação curta;
- sua área de atuação ou estudo;
- o propósito do blog;
- CTA para artigos;
- CTA para GitHub e/ou LinkedIn.

Exemplo de estrutura:

> Nome  
> Desenvolvedor focado em backend, Node.js e arquitetura de software.  
> Escrevo sobre aquilo que estudo, construo e aprendo na prática.

### Artigos recentes

Mostrar entre 3 e 6 artigos.

Cada artigo pode apresentar:

- categoria;
- título;
- pequeno resumo;
- nível de dificuldade;
- tempo de leitura;
- data.

### Trilhas em destaque

Exibir algumas trilhas importantes.

Exemplos:

- Node.js;
- TypeScript;
- Backend;
- JavaScript;
- Arquitetura de Software.

Cada trilha pode apresentar:

- nível;
- quantidade de artigos;
- descrição curta;
- CTA para acessar a trilha.

### Projetos em destaque

Selecionar os projetos mais relevantes.

Cada projeto pode mostrar:

- nome;
- descrição curta;
- stack;
- objetivo;
- link para estudo de caso;
- link para GitHub.

### Categorias ou tecnologias

Exibir as principais áreas abordadas no site.

Exemplos:

- Node.js;
- TypeScript;
- JavaScript;
- SQL;
- Arquitetura;
- DevOps.

### Newsletter

Bloco curto para inscrição.

A comunicação deve ser editorial, não comercial.

Exemplo:

> Receba novos artigos, trilhas e experimentos técnicos no seu e-mail.

### Rodapé

Pode conter:

- pequena apresentação;
- GitHub;
- LinkedIn;
- e-mail;
- RSS futuramente;
- navegação secundária.

## O que não deve ter

Evitar:

- informação demais acima da dobra;
- dezenas de cards;
- animações exageradas;
- excesso de efeitos visuais;
- textos muito longos;
- linguagem de marketing;
- aparência de agência criativa;
- visual de dashboard;
- excesso de badges;
- excesso de cores;
- blocos repetitivos;
- apresentação completa do currículo.

## Observações de UX

O usuário deve compreender o site em poucos segundos.

A Home deve direcionar, não explicar tudo.

# Página 2 — Artigos

## Para que a página serve

A página de artigos deve funcionar como a biblioteca principal do blog.

Seu objetivo é permitir que o visitante encontre conteúdo com facilidade.

## O que deve ter

- título da página;
- introdução curta;
- busca;
- filtros;
- lista ou grid de artigos.

### Filtros possíveis

- tecnologia;
- categoria;
- dificuldade;
- trilha;
- data;
- tema.

### Cada artigo pode mostrar

- título;
- resumo;
- categoria;
- tecnologia;
- dificuldade;
- tempo de leitura;
- data.

## O que não deve ter

Evitar:

- filtros demais simultaneamente;
- cards visualmente pesados;
- excesso de informações repetidas;
- paginação confusa;
- layout parecido com dashboard;
- thumbnails obrigatórias em todos os artigos.

## Observações de UX

O foco deve estar no título e no conteúdo, não na imagem.

A leitura visual deve ser rápida.

# Página 3 — Página de artigo

## Para que a página serve

Esta é uma das páginas mais importantes do projeto.

Ela deve demonstrar:

- conhecimento técnico;
- capacidade de comunicação;
- capacidade de ensinar;
- organização de raciocínio;
- profundidade;
- experiência prática.

## O que deve ter

### Cabeçalho

- categoria;
- título;
- resumo;
- data;
- tempo de leitura;
- dificuldade;
- tecnologias relacionadas.

### Índice lateral

O índice deve permitir:

- visualizar a estrutura do artigo;
- navegar entre seções;
- acompanhar a posição atual.

### Corpo do artigo

O conteúdo deve ter:

- largura confortável;
- bom espaçamento;
- hierarquia tipográfica clara;
- títulos bem definidos;
- parágrafos curtos;
- listas quando necessário.

### Blocos de destaque

Podem ser usados para:

- observações;
- alertas;
- conceitos importantes;
- boas práticas;
- erros comuns;
- conclusões intermediárias.

### Código

Usar código somente quando necessário.

Os blocos de código devem ter:

- linguagem identificada;
- boa legibilidade;
- botão para copiar;
- contraste adequado;
- suporte ao dark mode.

### Projeto relacionado

Sempre que possível, conectar o artigo a um projeto real.

### Navegação final

Pode conter:

- artigo anterior;
- próximo artigo;
- progresso na trilha;
- conteúdos relacionados;
- projeto relacionado.

## O que não deve ter

Evitar:

- largura de texto excessiva;
- excesso de código;
- parágrafos enormes;
- banners;
- pop-ups;
- sidebar cheia de elementos;
- muitos CTAs;
- elementos que distraiam da leitura.

## Observações de UX

A página precisa ser confortável para leitura média ou longa.

A prioridade absoluta é o conteúdo.

# Página 4 — Trilhas de aprendizado

## Para que a página serve

Organiza artigos em caminhos progressivos de conhecimento.

Ela demonstra que o site não possui apenas conteúdos isolados, mas uma organização intelectual.

## O que deve ter

Cada trilha pode mostrar:

- título;
- descrição;
- nível;
- quantidade de módulos;
- quantidade de artigos;
- pré-requisitos;
- objetivo.

### Exemplos de trilhas

- Node.js;
- TypeScript;
- Backend;
- SQL;
- Arquitetura;
- DevOps.

## O que não deve ter

Evitar:

- aparência de plataforma de cursos;
- gamificação exagerada;
- muitos indicadores;
- barras e badges em excesso;
- progressão artificial.

## Observações de UX

A trilha deve parecer um mapa de conhecimento, não um LMS.

---

# Página 5 — Página de trilha

## Para que a página serve

Mostra o caminho completo de aprendizado dentro de determinado assunto.

## O que deve ter

### Introdução

- nome;
- objetivo;
- nível;
- pré-requisitos;
- estimativa de conteúdo.

### Estrutura em módulos

Exemplo:

## Node.js

### 01 — Fundamentos

- O que é Node.js;
- Runtime;
- Processo Node.

### 02 — Concorrência

- Event Loop;
- libuv;
- Thread Pool.

### 03 — I/O

- Streams;
- Buffer;
- Filesystem.

### 04 — Backend

- HTTP;
- APIs;
- erros;
- validação.

### 05 — Produção

- profiling;
- observabilidade;
- performance.

### Progresso

Pode indicar:

- concluído;
- atual;
- próximo.

### Projetos relacionados

Mostrar projetos utilizados naquela trilha.

## O que não deve ter

Evitar:

- aparência de curso comercial;
- pontos;
- ranking;
- recompensas artificiais;
- elementos excessivamente lúdicos.

## Observações de UX

O visitante deve entender claramente:

1. onde começar;
2. o que estudar depois;
3. o que precisa saber antes;
4. como os assuntos se relacionam.

# Página 6 — Projetos

## Para que a página serve

A página de projetos é o portfólio técnico do site.

O objetivo não é apenas mostrar que algo foi construído, mas demonstrar o contexto e o conhecimento por trás da construção.

## O que deve ter

Cada projeto pode apresentar:

- nome;
- descrição;
- problema resolvido;
- tecnologias;
- status;
- estudo de caso;
- GitHub;
- demo, quando existir.

### Exemplo

**Node Runtime Lab**

Node.js · TypeScript · Vitest

Laboratório criado para estudar Event Loop, streams, concorrência e tratamento de erros em Node.js.

Links:

- Ver estudo de caso;
- GitHub;
- Artigos relacionados.

## O que não deve ter

Evitar:

- cards genéricos;
- projetos sem contexto;
- apenas screenshots;
- apenas lista de tecnologias;
- projetos fictícios usados somente para preencher espaço.

## Observações de UX

Priorizar poucos projetos relevantes em vez de dezenas de projetos pequenos.

# Página 7 — Estudo de caso do projeto

## Para que a página serve

Esta página demonstra como você pensa como desenvolvedor.

Ela deve ir além do código e mostrar decisões, problemas e aprendizados.

## O que deve ter

### Problema

Qual problema o projeto resolve?

### Contexto

Por que ele foi criado?

### Objetivos

O que você queria aprender ou demonstrar?

### Stack

Quais tecnologias foram utilizadas?

### Decisões técnicas

Explicar decisões relevantes.

Exemplos:

- por que Node.js;
- por que PostgreSQL;
- por que determinada arquitetura;
- por que determinada biblioteca.

### Arquitetura

Pode incluir diagramas.

Exemplo:

```text
Client
   ↓
API
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
```

### Trade-offs

Mostrar ganhos e perdas das decisões tomadas.

### Desafios

Quais problemas apareceram durante o desenvolvimento?

### Testes

- estratégia;
- tipos de testes;
- ferramentas.

### Performance

Quando relevante:

- métricas;
- gargalos;
- profiling;
- otimizações.

### Aprendizados

O que o projeto ensinou?

### Conteúdo relacionado

- artigos;
- trilhas;
- tecnologias.

### Links

- GitHub;
- demo;
- documentação.

## O que não deve ter

Evitar:

- linguagem promocional;
- dizer apenas que o projeto foi "desafiador";
- mostrar somente a interface;
- listar tecnologias sem explicar decisões;
- esconder erros e limitações.

## Observações de UX

Mostrar trade-offs e limitações aumenta a credibilidade técnica.

# Página 9 — Sobre

## Para que a página serve

Apresenta quem você é profissionalmente e como você pensa sobre desenvolvimento.

## O que deve ter

- apresentação;
- trajetória;
- áreas de interesse;
- tecnologias;
- forma de estudar;
- objetivos;
- projetos importantes;
- links profissionais.

### Timeline opcional

Exemplo:

**2026**  
Aprofundamento em Node.js e arquitetura backend.

**2027**  
Expansão para novos temas e tecnologias.

## O que não deve ter

Evitar:

- copiar currículo completo;
- texto autobiográfico excessivamente longo;
- informações pessoais sem relação profissional;
- listas intermináveis de tecnologias.

## Observações de UX

A página deve complementar LinkedIn e GitHub, não duplicá-los.

# Página 10 — Agora

## Para que a página serve

Mostra o momento atual da sua evolução profissional.

## O que deve ter

### Atualmente estudando

Exemplo:

Arquitetura backend.

### Construindo

Exemplo:

Blog técnico e laboratórios Node.js.

### Lendo

Livros ou materiais atuais.

### Explorando

Tecnologias ou conceitos em investigação.

## O que não deve ter

Evitar:

- atualização diária;
- conteúdo irrelevante;
- transformar em rede social;
- informações pessoais demais.

## Observações de UX

Esta página pode ser simples e pequena.

# Página 11 — Busca

## Para que a página serve

Permite encontrar rapidamente qualquer conteúdo do site.

## O que deve pesquisar

- artigos;
- trilhas;
- projetos;
- tecnologias.

### Exemplo

Busca:

`event loop`

Resultados:

**Artigos**  
Event Loop no Node.js

**Trilhas**  
Node.js Runtime

**Projetos**  
Node Runtime Lab

## Possíveis interfaces

- página `/buscar`;
- modal;
- Command Palette;
- atalho `Ctrl + K` ou `⌘ + K`.

## O que não deve ter

Evitar:

- busca limitada apenas a títulos;
- resultados sem contexto;
- interface muito complexa.

# Direção geral do projeto

O site deve funcionar simultaneamente como:

- blog técnico;
- portfólio;
- base de conhecimento;
- registro da evolução profissional.

O principal diferencial não deve ser mostrar quantas tecnologias você conhece.

O site deve mostrar:

- como você pensa;
- como resolve problemas;
- como organiza conhecimento;
- como constrói software;
- como explica conceitos;
- como toma decisões técnicas;
- como analisa trade-offs;
- como aprende.

---

# Direção visual

## Estilo

- minimalista;
- moderno;
- editorial;
- sério;
- limpo;
- profissional;
- autoral.

## Tema

- tema claro como padrão;
- dark mode disponível.

## Evitar

- aparência de agência criativa;
- animações exageradas;
- cara de template;
- excesso de informação na Home;
- aparência de documentação pura;
- aparência genérica de site criado por inteligência artificial;
- dashboards;
- cards demais;
- monoespaçada em excesso;
- efeitos neon;
- excesso de badges;
- excesso de gradientes.

---

# Princípio central

O GitHub mostra o código.

O site deve mostrar o raciocínio por trás do código.

Os três pilares principais do projeto devem ser:

1. **Artigos** — demonstram conhecimento e comunicação;
2. **Trilhas** — demonstram organização e domínio conceitual;
3. **Projetos e estudos de caso** — demonstram aplicação prática e tomada de decisão.
